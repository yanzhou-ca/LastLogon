# LastLogon: QA review and audit

Date: 2026-11-12 · Build under test: `main` @ `7c1f57a` (clean tree) · Reviewer: Claude (automated QA pass)

## 1. Verdict

**Conditionally releasable for a small, informed group; not yet for wider rollout.**
The core idea works and is faithfully ported: on the test machine the C# scan returns the same
`NTUSER.DAT` time as the original PowerShell one-liner (section 5). The code shows real security
care (injection defences, path validation, bounded concurrency) and all 173 unit tests pass,
stable over 12 consecutive runs.

Two **High** defects should be fixed before wider use, plus a short list of **Medium** ones:

| # | Severity | Defect |
|---|---|---|
| D-01 | High | Pressing Enter during a running scan starts a second scan; the first can no longer be cancelled, `IsScanning` goes false early, results interleave |
| D-02 | High | One unreadable profile folder throws away every profile of that computer and reports a misleading "access denied, you need admin" |
| D-03 | Medium | The 10 s timeout covers the whole computer and is all-or-nothing: servers with many profiles return nothing |
| D-04 | Medium | History account filters are wrong: "Local" misses FQDN / long names, "Domain" includes machine accounts |
| D-05 | Medium | "Interactive" filter hides lock, unlock and user-logoff events |
| D-06 | Medium | History "To" time is frozen at window creation, so a long-open window silently misses the latest events |
| D-07 | Medium | Short-name resolution is used in places the design says it never is |

### Fix status

**D-01 and D-02 are fixed in the working tree (uncommitted)**, test-first. Seven regression tests were
added; five failed against the old code for the expected reasons and all 180 tests now pass (20/20
consecutive runs). The Release/x64 build of the WPF project succeeds with the same 10 analyzer warnings
as before, and the original scratch repros `R1`-`R3` now pass. See the "Resolution" note under each defect.
Everything else in this report is still open, except for the follow-up below.

**Follow-up, requested after the first field report (uncommitted).** A scan row that fails with
"access denied" for the whole computer now runs the same test as the **Test connection** button and
adds, right after the reason, which address each way of naming the computer resolves to and whether it
could be read, for example `Tried: pc01.corp (10.0.0.5) failed, Windows error 5; pc01 (10.0.0.9)
reachable. The names resolve to different addresses, so they reach different computers.` Two names that
reach different computers is the usual reason a correct account is refused. Only an access failure of the
whole computer is probed (an unreachable computer would slow a bulk scan down), the probe may take at most
three times the per-computer timeout, and a failing or slow probe leaves the row unchanged. The Test
button prints the same text. This also fixes the missing timeout on `Dns.GetHostEntry` noted in D-20
(now 5 s per name). 11 tests added (191 total).

**Second follow-up, requested after asking what happens when the user has no record (uncommitted).**
By user now reports every computer it checks. A reached computer without the profile gets a `NoProfile`
row (it was silently left out before), and the status line reads for example `Done. 12 computer(s)
checked: 3 with a profile, 8 without, 1 could not be checked.` (`Cancelled. 5 of 12 computer(s) checked: …`
when stopped). When the exact folder is not there and `C:\Users` cannot be listed, the row is `NoProfile`
and says a folder with a suffix could not be looked for, instead of an access-denied row that blamed the
account. The Open folder button stays off for `NoProfile` rows, whose folder does not exist. By computer
is unchanged. The spec was amended to match. 9 tests added (200 total).

**The Test connection button was removed (uncommitted).** The window no longer has the button, its label or
its handler. Findings that mention it (D-07, D-14) describe the earlier build; D-14 no longer applies. The
connection check itself stays in Core, because a denied scan row uses it to show which address each name
reaches.

## 3. Defect log

Severity: **High** wrong or lost results, or a broken control, in normal use · **Medium** wrong in common
conditions, or a design/security rule violated · **Low** edge case, hardening, hygiene.
Confidence: *Confirmed* = reproduced by a test here · *Code* = read in the source, not executed ·
*Verify* = plausible, needs the target environment.

### D-01 Re-entrant scan from the Enter key (High, Confirmed at view-model level)
- `ScanWindow.xaml.cs:149-154`: Enter in any input calls `StartScanAsync()` and never checks `IsScanning`. The Scan button is disabled during a scan; this path bypasses that.
- History: `LogonHistoryViewModel.cs:182-186` calls `ClearResults()` and **disposes the running scan's `CancellationTokenSource` without cancelling it**, then replaces it. Cancel now reaches only the newest scan.
- Both view models: the older scan's `finally` sets `IsScanning = false` (`LogonHistoryViewModel.cs:238`, `MainViewModel.cs:104`) while the newer one is still running, so Scan is re-enabled mid-scan.
- Repro `R1`: first token cancelled after second scan started = **False**; after `Cancel()` = **False** (second = True); `IsScanning` after the first finished = **False** while the second ran. `R2` (profile scan): same, status "Cancelled. 0 result(s)." while scan 2 runs.
- Fix: guard `StartScanAsync` (`if (IsScanning) return;`) **and** make the view models cancel the previous scan; only the scan that owns the current token may clear `IsScanning`.
- **Resolution (fixed, uncommitted).**
  - `ScanWindow.StartScanAsync` returns at once while a scan or an AD search is running, so Enter no longer starts a second scan.
  - Both view models also protect themselves: a new scan cancels the running one first, and each scan carries a generation number. A replaced scan adds no results, writes no status, and does not reset `IsScanning` or the cancellation source; each scan disposes only its own source. `LogonHistoryViewModel.Cancel()` tolerates a source that was just disposed.
  - Tests: `LogonHistoryViewModelTests.ScanAsync_StartedWhileScanning_*` (3), `MainViewModelTests.Scan_StartedWhileAnotherIsRunning_KeepsScanningUntilTheNewScanEnds`.
  - Not covered by an automated test: the `StartScanAsync` guard itself, which lives in the WPF project (see section 4, point 5). It is a one-line check; confirm it by pressing Enter twice during a slow scan.
  - Left as is: invalid input typed while a scan runs still clears the result list in the view model. The UI guard makes that unreachable from the window.

### D-02 One bad profile folder discards the whole computer (High, Confirmed)
- `ProfileScanner.cs:49-58` builds the list inside one delegate; `ReadProfile` (`:229-235`) can throw, and `SmbProfileFileSystem.GetNtUserDatTime` (`IProfileFileSystem.cs:40-55`) only swallows `FileNotFound` / `DirectoryNotFound`.
- Repro `R3`: 5 profiles, one throws `UnauthorizedAccessException` → **1 row** ("AccessDenied … The account has to be an administrator on …"), 4 good profiles lost. Stale or ACL-locked profile folders on shared machines are common, and the advice shown is wrong because the account is an administrator.
- Fix: catch per profile and emit a row for that profile (`AccessDenied` / `Error`) while keeping the others.
- **Resolution (fixed, uncommitted).** `ProfileScanner` now catches `UnauthorizedAccessException` per profile and adds a row for that folder: status `AccessDenied`, the system's reason (which names the file), and "The other profiles on this computer could be read." (no misleading administrator advice). Deliberate limits:
  - If **no** profile can be read, the computer is still reported once with the full guidance, as before.
  - Only access problems are attributed to one profile. Any other failure (for example a lost connection) still ends the computer as `Offline` / `Error`, because every later profile would fail the same way.
  - Tests: `ScanComputer_OneUnreadableProfile_KeepsTheProfilesThatCanBeRead` (failed first), plus two guards that pass before and after: `ScanComputer_NoProfileCanBeRead_ReportsOneRowForTheComputer`, `ScanComputer_ConnectionLostWhileReadingAProfile_ReportsTheComputerAsOffline`.
  - Not changed: D-03 (the 10 s budget is still per computer).

### D-03 Timeout is per computer and all-or-nothing (Medium, Confirmed)
- `ProfileScanner.cs:21` (10 s default) wraps the entire enumeration. Repro `R4`: 30 profiles at 100 ms each, 1 s budget → one `TimedOut` row, ~10 profiles already read are discarded. Terminal servers or lab machines with hundreds of profiles will always time out.
- Same family for history: `LogonEventScanner` keeps already-read events on timeout (good) but the 10 s default budget includes remote XPath evaluation, so a busy Security log over a 3-90 day range will often end as `TimedOut` with partial data. It is not configurable in the UI.
- Fix: per-profile budget plus partial results, and expose the timeout.

### D-04 History account filters are wrong (Medium, Confirmed)
- `LogonHistoryViewModel.cs:309-319` compares `AccountDomain` with the text the operator typed as the computer name.
- `R5`: computer entered as `pc01.corp.example`, local account domain `PC01` → shown under **Domain** accounts, **0** under Local. `R5b`: names over 15 characters (NetBIOS truncation) never match Local.
- `R6`: machine accounts (`PC02$`) pass the **Domain accounts** filter. The reference script excludes SYSTEM and `*$` by default ("Exclude System Accounts", on).
- Fix: compare against the first label truncated to 15 characters; treat `$`-suffixed names and SYSTEM / LOCAL SERVICE / NETWORK SERVICE / ANONYMOUS LOGON / DWM-* / UMFD-* as system; add an "exclude system and machine accounts" option, default on.

### D-05 "Interactive" filter hides lock/unlock/logoff (Medium, Confirmed)
- `LogonHistoryViewModel.cs:328-334`: events with no `LogonType` (4647, 4800, 4801, 4672) fall into **Other**. `R7`: Interactive → only 4624; Other → 4800.
- Fix: classify by event ID when `LogonType` is absent (4647/4800/4801 → Interactive).

### D-06 "To" time frozen at window creation (Medium, Code)
- `ScanWindow.xaml.cs:44-46` fills both text boxes once, truncated to the minute, from values set in the view-model constructor (`LogonHistoryViewModel.cs:55-56`). Leave the tool open for two hours, switch to Logon history, press Scan: the newest two hours are excluded without notice. Spec says the default is "the last three days".
- Fix: refresh the defaults when switching to the mode, or treat an untouched box as "now".

### D-07 Short-name fallback contradicts the stated invariant (Medium, Confirmed)
`ComputerTarget.cs:9-16` says every network path addresses the same fully qualified host and none falls back to short-name resolution (which an on-path attacker can poison). In practice:
- **Test connection** always tries the bare short name as the second candidate, also in the default *Domain-qualified* mode (`ConnectionTest.cs:135-144`). The fallback fires exactly when the FQDN does not resolve, which is when LLMNR / NBT-NS poisoning wins, and sends the elevated operator's credentials. The tooltip at `ScanWindow.xaml:80` says domain-qualified "cannot be redirected".
- When the domain cannot be determined, `Qualify` silently returns the short name (`ComputerTarget.cs:83-86`). The SMB scan refuses (`IProfileFileSystem.cs:25-31`) but the **Security-log query** (`WindowsLogonEventSource.cs:20`) and **Open folder** (`ScanWindow.xaml.cs:580`) fall back. Repro `R11`: log host `pc01`, Explorer path `\\pc01\C$\Users`, SMB `InvalidOperationException`.
- Fix: make the second Test attempt opt-in with a visible warning; make `Qualify`/`UncPath` throw (or return a failure) like `Root()` does.

### D-08 Domain lookup blocks the UI thread and failure is cached (Medium, Code; not reproducible on a workgroup host)
- The constructor calls `UpdateComputerTargetHint()` (`ScanWindow.xaml.cs:52`) → `ComputerTarget.DnsDomain` → `GetActiveDirectoryDomain()` waits up to 3 s on the UI thread (`ComputerTarget.cs:152-158`).
- `_dnsDomain ??= ResolveDnsDomain()` (`:63`) stores an empty string, which is non-null, so a failed lookup (VPN not yet up) is cached until restart.
- Fix: resolve asynchronously after the window shows; do not cache empty results.

### D-09 Enter starts the scan in a "one per line" box (Low, Code)
`ScanWindow.xaml:76` and the label promise "one per line", but Enter runs the scan; only Shift+Enter inserts a line (`ScanWindow.xaml.cs:151`). `AcceptsReturn="True"` is now misleading. Add a hint, or require Ctrl+Enter in the multi-line box.

### D-10 Input validation vs Active Directory (Medium, Confirmed)
- `InputParser.cs:37` rejects `_`; Windows accepts it in computer names. `R8`: `pc_01` and a three-name list fail. One such name loaded **From AD** blocks the whole scan.
- The message `MainViewModel.cs:61` / `LogonHistoryViewModel.cs:160` says "paths **and domains** are not allowed" although FQDNs are accepted and the label says "short or full name" (`R8b`). It also never names the offending token.
- `R8c`: `localhost` becomes `localhost.<domain>`, so the local machine cannot be queried by that name (the reference script defaults to `localhost`).

### D-11 Profile export and grid are culture-dependent (Medium, Confirmed)
`Models.cs:17-18` and `ResultExporter.cs:36-37` format with the current culture. `R15`: `th-TH` → `2568-03-04 15:30`, `ar-SA` → `1446-09-04 15:30`, `da-DK` → `2025-03-04 15.30`. The logon-event export already uses `InvariantCulture` (`ResultExporter.cs:59`), so the two exports disagree. Wrong years in an exported audit file is silent corruption. Analyzer CA1305 flags exactly these lines.

### D-12 Parser only survives `FormatException` (Low, Confirmed)
`LogonEventParser.cs:26-29,76` use `int.Parse`; an oversized value throws `OverflowException`, which `LogonEventScanner.cs:155` does not catch. `R9`: the computer ends as `Error` and the later events are lost, contradicting commit 6063fb2 ("a record that cannot be parsed no longer discards the rest"). Windows generates these values, so practical impact is low; use `TryParse`.

### D-13 Future timestamps corrupt the numeric column (Low, Confirmed)
Clock skew gives a negative `DaysAgo`; the CSV guard turns `-2` into `'-2` (`R13b`, `ResultExporter.cs:79`). Clamp at 0 or exempt numeric columns.

### D-14 Test connection does not test what History needs (Medium, Code)
`Test_Click` (`ScanWindow.xaml.cs:225-263`) always lists `\\host\C$\Users` over SMB. In Logon history mode the query uses RPC to the Event Log service (Remote Event Log Management), so "Reachable" can precede "The computer is unreachable" (`LogonEventScanner.cs:273-274`). The offline message gives no remedy (firewall rule *Remote Event Log Management*). Note the reference README's "WinRM is required" is not true of either implementation.

### D-15 `requireAdministrator` and the "not elevated" guidance (Medium, Verify)
- `app.manifest:14` forces elevation; `ProfileScanner.cs:278-283` tells operators the C$ share "is refused" when not elevated; commit 3b7ffea justifies it with a filtered token.
- Microsoft's [KB 951016](https://support.microsoft.com/help/951016) says a **domain** account in the target's Administrators group gets a **full** token remotely; filtering applies to **local** accounts. The spec's scenario is a domain admin ("AD admin account already signed in"). If that holds in your estate, the elevation requirement and the guidance are misleading, and elevation widens the blast radius of a process that renders attacker-influenced strings (usernames in failed-logon events).
- Verify: same domain admin account, non-elevated vs elevated, same target. On the test machine a loopback read worked non-elevated (local account), which proves nothing either way.

### D-16 Dependencies and runtime lifecycle (Medium)
- **.NET 8 reached end of support on 10 Nov 2026** ([Microsoft .NET blog](https://devblogs.microsoft.com/dotnet/dotnet-8-9-end-of-support/)). Every project targets `net8.0`; the `standalone-*` profiles bundle that runtime, so shipped copies stop receiving patches. .NET 10 (LTS) SDK is already installed.
- Test project only: `System.Net.Http 4.3.0` ([GHSA-7jgj-8wvc-jh57](https://github.com/advisories/GHSA-7jgj-8wvc-jh57)) and `System.Text.RegularExpressions 4.3.0` ([GHSA-cmhx-cq75-c4mj](https://github.com/advisories/GHSA-cmhx-cq75-c4mj)), both rated High, arrive transitively. Not shipped, but they fail an audit gate. `xunit 2.5.3` is flagged deprecated.

### D-17 Directory search (Low–Medium, Verify)
- `AdComputerSearch.cs:39-41`: `PageSize 500` with `SizeLimit 5000`. Sources disagree on whether `SizeLimit` applies with paging ([docs](https://learn.microsoft.com/en-us/previous-versions/ms180880(v=vs.90)) vs community reports). Either it silently truncates at 5000 or it is inert, and nothing tells the operator (`MainViewModel.cs:124`).
- The result includes disabled and stale accounts (many offline timeouts) and uses `name`, not `dNSHostName`.
- A "relative" OU such as `OU=Sales` (the error text's own example, `AdComputerSearch.cs:70-73`) is bound as `LDAP://OU=Sales`; whether ADSI completes it with the default naming context is **unverified** and I suspect it does not. Test in a domain.
- Validator hardening: `IsValidDistinguishedName` accepts `OU=Sales;DC=evil;DC=com` and `OU=Sales+DC=evil` (`R14`). If ADSI honours `;` as an RDN separator, the foreign-domain check is bypassed. Reject `;` and `+` (cheap, no downside). The input is operator-typed, so exposure needs a pasted-in value.

### D-18 Hardening and hygiene (Low)
- Standalone single-file builds set `IncludeNativeLibrariesForSelfExtract=true` (`standalone-win-x64.pubxml:15`): native WPF libraries are extracted to a user-writable temp folder and loaded by an elevated process. (UAC is not a servicing security boundary, but this is easy to avoid.) *Verify* by running the published exe and inspecting `%TEMP%\.net`.
- `Import_Click` reads any file whole into the text box (`ScanWindow.xaml.cs:544-556`); the unhandled-exception dialog shows the raw message (`App.xaml.cs:18-26`).
- `ScanWindow.IsElevated()` (`:376-387`) duplicates `RunContext.IsElevated`. `CA1416` is suppressed project-wide, hiding Windows-only API use in a `net8.0` library.
- Dead or stale: `MainWindow.xaml`, `LookupWindow.xaml` (excluded from the build, `LastLogon.csproj:29`), `Package.appxmanifest` (references `Square150x150Logo.png` but assets are `*.scale-200.png`; app is unpackaged), `Microsoft.Windows.SDK.BuildTools`, `EnableMsixTooling`.
- No `README.md` or `LICENSE`. Specs say "WinUI 3" / "draft, awaiting approval" for work that is WPF and built; `publishing.md` says ~60 MB, the pubxml comment ~70 MB.

### D-19 Accessibility (Low, Code)
Stale rows are marked only by an orange background (`ScanWindow.xaml.cs:479-484`), with no text or icon. Fixed `#666` / `#DDD` / `#FAFAFA` colours ignore High Contrast themes. Not tested with a screen reader.

### D-20 Observations (no action required, but worth knowing)
- ~~By-user mode lists only computers that have the profile plus failures, so the summary does not say how many were checked.~~ Fixed in the second follow-up below.
- History inserts each of up to 50 000 events through the dispatcher with an O(n) list insert. Commit 6063fb2 measured filtering, not UI insertion. **Not measured here.**
- ~~`Dns.GetHostEntry` has no timeout~~ Fixed in the follow-up above: each name now gets at most 5 s to resolve.

## 5. Verified correct (so it is not re-litigated)

- **Parity with the original one-liner.** Same profile: PowerShell `2026-10-14 4:46:08 PM`, C# `2026-10-14 16:46`. System folders (`Public`, `Default`, `Default User`, `All Users`, `desktop.ini`) are skipped; `ConnectionTest` reported "5 profile folder(s) readable".
- **Event Log XPath.** The shape produced by `WindowsLogonEventSource.BuildXPath` is accepted by the Event Log service (`wevtutil`, Application log). It contains no operator text.
- **LDAP filter escaping** (`\ * ( ) NUL`) is correct; tested.
- **Spreadsheet injection.** Leading whitespace, tab and NBSP before `= + - @` are neutralised in CSV and in the clipboard format; line breaks are stripped from TSV (`R13`).
- **Path-segment guard.** Hypothesis "`.. ` or `...` as a profile name escapes `Users\`" was **refuted** at the .NET layer: `Path.GetFullPath` keeps the segment (`R10`). Win32 / SMB-server normalisation was not tested.
- **Explorer launch** uses `ArgumentList` with validated names; no secrets, credentials or tokens are stored or logged; no network call other than SMB, Event Log RPC and LDAP.
- **XML parsing** uses named fields, not localised message text (better than the reference script, which regex-parses `Event.Message`). Note `XDocument.Parse` enables DTD processing with a 10 M character entity cap; the input is Windows-rendered, so this is acceptable, but a hardened `XmlReader` costs nothing.
